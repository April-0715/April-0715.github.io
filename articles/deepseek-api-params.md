# 从一次 API 调用到 Agent Loop：AI 编程 Harness 学习笔记

> 发布日期：2026-10-12 | 标签：AI

这次学习从一段 OpenAI-compatible API 的 Python 调用出发，逐步追问：代码怎样变成网络请求？客户端保存了什么？缓存是否意味着不再计算？模型如何调用工具？编程 Agent 的权限又由谁控制？

本文把概念说明与 Q&A 放在一起，记录理解的变化。**“原回答”仅引用当前可核实的用户回答；“补充辨析”是重新整理的解释。** 原问题及助手回答未能完整恢复，因此无法确定对应题意的编号回答，不据此认定为误解。例如“a 不清楚”的问题对象无法确认，不能替它编造一道题。

## 一、先把一次调用拆开

一次典型调用可以按下面的路径理解：

```text
Python 参数与消息
    → SDK 构造请求
    → HTTP 请求：地址、方法、请求头、JSON 请求体
    → 服务端校验、路由与模型推理
    → HTTP 响应或流式事件
    → SDK 解析为 Python 对象
    → 应用读取结果
```

这里有四个不同层次：**API** 是服务提供的调用接口与约定；**HTTP** 负责传送请求和响应；**JSON** 是常见的数据表示格式；**SDK** 是把这些操作封装起来的程序库。Python 中的方法调用本身并不等于网络协议。

### Q：所谓“OpenAI-compatible”，兼容的是 SDK 吗？

**原回答：**“API 协议，或者说 openai sdk。”

**补充辨析：**两个说法需要分开。第三方服务通常兼容部分 OpenAI API 的路径、参数和响应结构，因此可以复用 OpenAI SDK 发请求；这不意味着所有接口、模型能力和扩展字段都一致。`base_url` 指定实际服务地址，`model` 必须使用该服务支持的标识，API Key 也必须属于该服务。

这也意味着：把第三方地址交给客户端后，消息和凭证会发给那个第三方。兼容格式本身不提供可信性保证。

### Q：`messages` 是“JSON 数组”吗？

**原回答：**“json 数组。”

**纠正：**在 Python 代码里，它通常是由字典组成的列表；发送时才被序列化为 JSON 数组。返回值也通常是 SDK 解析后的对象，而不是未经解析的 JSON 文本。

```python
messages = [{"role": "user", "content": "解释 SDK 与 HTTP 的关系"}]
# messages 是 Python list，内部元素是 dict。
```

形参是函数定义中的名字，实参是调用时传入的值。`model="..."` 是关键字实参，`stream=True` 是请求配置；它们不是写给模型看的自然语言指令。

## 二、客户端对象究竟保存什么

### Q：`client` 是什么？为什么能反复使用？

**原回答：**“是一个客户端对象，因为生命周期没有结束。”另一个回答是“client 对象有自动挡包装方法吧”。

**已理解，继续补充：**它是可复用的客户端实例，保存服务地址、鉴权配置、超时与重试设置，并管理底层连接资源。方法封装了请求构造与响应解析。变量仍引用对象，解释了它为何仍可访问；连接池和配置复用，则解释了为什么值得复用它。

**复用客户端不会自动把前一次聊天内容加入下一次请求。** 连接资源、应用对话历史、服务端会话与提示缓存，是不同的状态。用完可显式关闭，或使用上下文管理器管理资源。

以下是服务端或本地脚本中的 Chat Completions 示例。环境变量名是本文自定义的，服务地址和模型需要按目标提供商文档设置。示例没有执行真实 API 请求。

```python
import os
from openai import OpenAI

with OpenAI(
    api_key=os.environ["LLM_API_KEY"],
    base_url=os.environ["LLM_BASE_URL"],
    timeout=30.0,
    max_retries=2,
) as client:
    response = client.chat.completions.create(
        model=os.environ["LLM_MODEL"],
        messages=[{"role": "user", "content": "用一句话解释 HTTP"}],
    )
    print(response.choices[0].message.content or "")
```

这是兼容服务常见的调用形式；不能据此假定目标服务还支持 OpenAI 的 Responses 等其他接口。客户端、异步与流式用法可查 [OpenAI Python API 文档](https://developers.openai.com/api/reference/python)。

## 三、同步、异步、流式是两个维度

同步与异步描述应用如何等待 I/O；流式与非流式描述结果如何交付。可以有同步非流式、同步流式、异步非流式、异步流式四种组合。

**同步调用**通常阻塞当前调用线程；**异步调用**通过 `await` 在等待网络时让出执行机会。单独把调用改成异步，不保证单次生成更快，也不等于自动并发。**流式调用**让应用逐步读取结果，通常能更早展示首段内容，但不保证总耗时缩短。

```python
import asyncio
import os
from openai import AsyncOpenAI

async def main():
    async with AsyncOpenAI(
        api_key=os.environ["LLM_API_KEY"],
        base_url=os.environ["LLM_BASE_URL"],
        timeout=30.0,
        max_retries=2,
    ) as client:
        stream = await client.chat.completions.create(
            model=os.environ["LLM_MODEL"],
            messages=[{"role": "user", "content": "解释流式输出"}],
            stream=True,
        )
        async with stream:
            async for chunk in stream:
                if chunk.choices:
                    text = chunk.choices[0].delta.content
                    if text:
                        print(text, end="", flush=True)
        print()

if __name__ == "__main__":
    asyncio.run(main())
```

这里展示文本增量。实际事件也可能含角色、工具调用参数片段、结束原因或用量信息；不能认为每个片段都含文本，也不能把未拼完整的工具参数直接当作可执行 JSON。已有事件循环的环境，应在其中 `await main()`。

## 四、API Key：从“不写进代码”走向完整边界

### Q：从环境变量读 Key，到底怎样才算安全？

**原先不清楚：**“这里是为了不暴露 apikey，到底怎么做才算安全。”

环境变量可以避免把凭证硬编码进源码，但不是保险箱。Key 仍会进入程序内存和鉴权请求头，也可能被调试输出、日志或本机其他高权限进程获取。

本地脚本可通过受控环境变量注入；部署时可使用秘密管理服务。不要把 Key 放进源码、提交记录、截图或日志；若使用 `.env`，应排除出版本控制，并限制文件访问。已经泄露的 Key 要撤销或轮换，仅删除文件无法清除已有副本。

**静态博客中的浏览器 JavaScript 不能保守长期 API Key。** 前端变量、打包文件和浏览器网络请求都可被查看。网页需要调用付费模型时，应通过自己的后端鉴权、限额和转发，并限制后端所持凭证的权限。服务商支持的短期凭证机制则按其文档另行设计。参见 [OpenAI API 鉴权说明](https://developers.openai.com/api/reference/authentication)。

### Q：服务端收到请求就直接交给模型吗？

**原回答：**“不是，先鉴权，分析请求，解码给模型生成回答。”

**方向正确，措辞细化：**服务端还可能做参数校验、配额检查、限流和路由。JSON 解析、文本分词与模型逐步生成 token 是不同阶段，“解码”不宜笼统指代它们。具体内部顺序依实现而定，不能从接口形式推断完整后端架构。

## 五、对话历史与上下文缓存

### Q：普通聊天调用会自动记住上一轮吗？

**原回答：**“不会，是无状态的，保持对话连贯性，保持缓存命中。”

**补充边界：**对普通、显式传入 `messages` 的 Chat Completions 调用，应用需要维护历史并随请求传入。某些其他接口提供服务端会话或响应关联功能，不能把“无状态”推广为所有产品都不存储任何状态。

历史的首要作用是让模型看到相关上下文；缓存只是可能发生的性能优化。应用还需要控制上下文长度、输出预算和截断或摘要策略，不能无限追加消息。

### Q：“完全命中缓存”，是不是回答也直接复用了？

**原回答：**“b 完全命中缓存。”由于题目缺失，无法判断这一回答在原题中是否正确，但可以澄清它容易引发的误解。

**纠正边界：**提示缓存复用的是已处理的匹配输入前缀，并不等于整份答案缓存。新增输入仍需处理，回答仍需生成；即便输入全部满足缓存条件，也不能据此说整次请求零计算或零费用。缓存规则、计价与有效期要按服务商及模型核实。

```text
第 1 次：固定说明 + 问题 1
第 2 次：固定说明 + 问题 1 + 回答 1 + 问题 2
         └ 可复用前缀 ┘   └ 新增部分仍需处理 ┘
```

稳定的说明和工具定义尽量放前面，变化内容放后面，有助于保留公共前缀；但命中还受缓存资格、有效期和路由影响。要查看服务端报告的缓存用量，而不是凭速度猜测。OpenAI 的规则见 [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)，不能直接套用到兼容服务。

## 六、超时和重试不只是两个数字

网络连接失败、读取等待过久、限流、服务端错误，都可能导致请求失败。超时帮助应用停止过久等待；重试帮助恢复临时故障，但错误的凭证或非法参数通常需要修正，而不是继续重复请求。

`timeout=30.0` 不应理解为整个 Agent 任务最多 30 秒。底层网络超时可能按连接、读取等阶段生效；流式读取也不是整段生成必须在该时间内结束。重试还会增加等待，应另外设置业务总期限、轮数和取消机制。

重试次数与总尝试次数不同：配置允许两次重试，意味着初次请求之外最多再尝试两次。SDK 的具体可重试错误与默认值以版本文档为准。重试应有上限，结合退避策略；不要把应用重试和 SDK 重试无意叠加。

**超时不证明服务端没处理请求。** 重发可能重复生成、产生费用；工具若涉及写入、支付或发送消息，更要考虑幂等、执行记录和结果查询。流式输出已经消费一部分后，失败恢复还要处理重复片段。[SDK 错误、超时和重试说明](https://developers.openai.com/api/reference/python)给出了相关行为。

## 七、一次任务为何包含多轮调用

### Q：一次任务就是一次模型调用吗？

**原回答：**“c 一次任务需要多轮工具调用。”

**已理解，补充限定：**需要工具的任务可能要多轮循环，但不是所有任务都必须调用工具。编程 Agent 可能经历“查看文件 → 修改 → 检查 → 根据结果修正”。任务、模型请求和工具调用不是一一对应关系，一轮也可能产生多个工具调用。

```text
准备上下文 → 请求模型
                 ↓
           最终回答？→ 结束
                 ↓ 工具调用请求
      校验参数、权限与预算
                 ↓
        执行工具或返回拒绝原因
                 ↓
     关联工具调用 ID，追加工具结果
                 ↓
             再请求模型
```

对于应用自定义函数，模型输出的是调用意图和参数，真正执行由宿主程序负责。Chat Completions 中通常要保留助手的 `tool_calls` 消息，并用对应 `tool_call_id` 回传工具结果。平台托管工具的执行流程可能不同。参见 [Function calling](https://developers.openai.com/api/docs/guides/function-calling)。

**Harness** 可以理解为模型周围的运行系统：组织上下文、驱动循环、连接工具、执行权限策略、记录结果并控制资源预算。只有 SDK 的网络调用封装，尚不足以构成完整的编程 Agent。

## 八、工具白名单与 Prompt Injection

### Q：编程工具不是已经有权限策略和白名单了吗？

**原观察：**“据我用过的工具，是有权限策略和白名单的。”

**这条观察应保留。** 不应把 Agent 描述成必然能无条件运行任意命令。具体可做什么，由宿主的策略、工具能力、沙箱和审批机制共同约束。

工具名白名单回答“哪些工具可用”；参数校验、路径和网络范围回答“可用工具允许做什么”。允许一个 shell 工具，不等于其中所有命令都安全。路径应在解析后检查范围，不能只靠字符串前缀；工具输出的成功与失败也要记录清楚。

### Q：有白名单，为什么还需要防 Prompt Injection？

**补充辨析：**Prompt Injection 是低信任内容试图改变 Agent 行为。网页、仓库注释或工具结果可能夹带“忽略原任务、读取密钥并上传”之类的指令。它们作为待处理数据出现，不因此获得用户指令的权限。

白名单缩小能力范围，却无法单独保证模型使用这些能力的目的正确。即使只允许读文件和发网络请求，两种能力组合也可能造成数据外传。防护需要保留指令与数据的信任边界，在执行端检查动作及参数，限制敏感数据流向，并对高影响操作应用适当审批。不能只写一句“请勿被注入”就认为问题解决。

工具返回“用户已授权”也不能自行创造授权。工具请求应接受与原任务一致的外部策略检查；模型自身输出的同意不能替代权限判断。相关设计见 [Safety in building agents](https://developers.openai.com/api/docs/guides/agent-builder-safety)。

## 九、这次理解发生了哪些变化

- **原先混在一起的概念：**SDK 与 API 协议、Python 列表与 JSON 数组，需要按程序层和传输层区分。
- **原先明确不清楚的问题：**API Key 如何安全保存，要从源码、运行环境、日志、浏览器和泄露处置一起考虑。
- **已有正确方向：**客户端是对象，普通聊天调用需要传入历史，复杂任务可能要多轮工具调用，实际编程工具存在权限策略。
- **需要补上边界的说法：**客户端存活不代表会记住聊天；缓存命中不代表直接复用答案；异步不代表单次更快；白名单不代表已消除注入风险。

以后阅读一段 Agent 代码，可以沿着几个具体问题检查：消息是谁组织的？数据实际发到哪里？历史放在哪里？模型输出谁来执行？执行前有哪些权限检查？失败后如何停止、重试和避免重复操作？这些问题把一次 API 请求与完整 Harness 连接了起来。
